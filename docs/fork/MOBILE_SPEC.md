# Hushflow on iPhone and Android: plan and decisions

Status: proposal, 2026-10-25. Research only; no code yet. Builds on `SPEC.md` (engines, cleanup, guard) and `NOTES_SPEC.md` (meeting notes). Sources were accessed on 2026-10-25 unless another date is given.

## 0. Decisions at a glance

## 1. The platform facts that drive the decisions

**iOS**

- **A keyboard extension can't record, and it gets little memory.** No extension may use the microphone ([MacStories](https://www.macstories.net/notes/on-the-limitations-of-ios-custom-keyboards/)). The memory cap isn't documented; developers observe about 30–60 MB, and the extension is killed silently when it goes over ([Fleksy](https://fleksy.com/blog/limitations-of-custom-keyboards-on-ios)).
- **Recording can't start in the background.** An app can't start recording from the background (Apple DTS: apps "will not in general be allowed to start recording while in the background"). A recording started in the foreground continues, but it can't resume from the background after an interruption ([Apple forums thread 120038](https://developer.apple.com/forums/thread/120038)). So a session has to start with a visible trip to the app.
- **App Review 4.4.1** (verbatim): keyboards must "provide keyboard input functionality (such as typed characters)", "provide a method for progressing to the next keyboard", and "remain functional without full network access and without requiring full access". They must not "launch other apps besides Settings" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Our keyboard therefore needs real typing keys that work without Full Access.
- **What shipping apps do.** Wispr Flow's keyboard "Start Flow" opens the app, which starts a time-boxed _Flow Session_ (5 min, 15 min, 1 h, or never) and sends the user back; it needs Full Access ([Wispr docs, 2026](https://docs.wisprflow.ai/articles/7453988911-set-up-the-flow-keyboard-on-iphone)). Aqua (first release 2026-04-05) and Willow do the same bounce ([9to5Mac](https://9to5mac.com/?p=1048162), [TechCrunch, 2025-11-12](https://techcrunch.com/2025/11/12/willows-voice-keyboard-lets-you-type-across-all-your-ios-apps-and-actually-edit-what-you-said)), so App Review tolerates it in practice despite 4.4.1. There is no public API to return to the host app (FB22247647 answered "No"; [forum thread 843118, Aug 2026](https://developer.apple.com/forums/thread/843118)), and users complain about the "swipe back" step ([ruben.substack comments](https://ruben.substack.com/p/flow/comments)).
- **On-device proof.** LocalFlow (PR #11, merged 2026-10-11) runs Parakeet on the Neural Engine from a backgrounded app session: **40 ms warm for 2.4 s of audio, 165 MB peak** on an iPhone 15 Pro running iOS 26.6.2, a 67 s first Core ML compile, and a 3.2 GB peak on CPU only ([GitHub](https://github.com/ajbarryiii/LocalFlow/pull/11)). Muesli iOS uses the same App Group request/result pattern with FluidAudio Parakeet ([GitHub](https://github.com/Muesli-HQ/muesli-ios)).
- **The baseline to beat** is the free system dictation: Apple's mic key and Gboard voice typing, on device and with no setup. Our difference has to be visible in the first minute: cleanup ("no wait, Tuesday", fillers, lists), the personal dictionary, history, and hold-to-talk with live feedback.

**Android**

- **An IME can record in its own process** and commit text into any field. FUTO Voice Input, Transcribro (whisper.cpp + Silero VAD) and Voxscribe ship fully on-device voice keyboards ([FUTO](https://github.com/futo-org/voice-input), [Transcribro](https://github.com/soupslurpr/Transcribro), [Voxscribe](https://f-droid.org/packages/org.y20k.voxscribe/)). A voice IME can be reached from HeliBoard, SwiftKey, AOSP and similar keyboards through the voice subtype, but **not from Gboard or Samsung Keyboard** ([FUTO README](https://github.com/futo-org/voice-input)).
- **The bubble route (Wispr Flow Android)** pairs an overlay with an accessibility service that finds fields and inserts text. It needs "Display over other apps" plus accessibility, and the service drops after a force-stop ([Wispr docs, 2026-06-05](https://docs.wisprflow.ai/articles/3941699399-keyboard-and-screen-reader-accessibility-in-wispr-flow)). Under Play policy only tools for people with disabilities may declare `isAccessibilityTool`; everyone else needs a prominent disclosure and consent screen ([Play policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)).
- **Background mic:** a `microphone` foreground service must be started while an activity is visible, or from a notification or widget tap. An overlay window or being the current IME does **not** exempt an app from this while-in-use rule ([Android docs, updated 2026-10-23](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)). The bubble needs a session; the IME doesn't.

## 2. Product shape per platform (MVP)

**iPhone (iOS 26+):**

1. **Hushflow app:** a large record button (hold, or tap to keep recording) with copy and share; history; personal dictionary; the "Clean up my text" toggle; engine status; a lock-screen and Control Center control plus an App Intent ("Dictate to clipboard") for the Action Button.
2. **Hushflow Keyboard:** a compact QWERTY with a mic key, a globe key, return and delete. It types without Full Access (4.4.1). With Full Access and an active session, holding or tapping the mic records through the app and inserts the text with `textDocumentProxy`. Without a session, the mic key shows "Start Hushflow". That opens the app (the gray area); the app starts the session and shows "Swipe back to your app". A Release fallback that launches nothing is "Start a session in the app, then come back", which is the compliant path described in thread 843118.
3. **Session:** the main app keeps one `AVAudioEngine` input open with `UIBackgroundModes=audio` and drops the samples between dictations. It times out after 5, 15 or 60 minutes (default 15) and ends on lock or interruption. The keyboard and the app talk through App Group files, which are authoritative, with Darwin notifications as hints. Each result is claimed once by renaming its file. This is LocalFlow's design.
4. Not in the MVP: voice editing of a selection, iPad hardware-keyboard hotkeys, sync with the desktop app.

**Android (API 31+):**

1. **Hushflow Voice Keyboard (IME):** a voice panel with a large mic key (hold or tap), live waveform, space, delete, return, "undo cleanup" and "switch keyboard" (`switchToPreviousInputMethod`). It is also exposed as a voice subtype, so HeliBoard, SwiftKey and similar keyboards can jump to it. It records in the IME, sends audio to the `:engine` process and commits through `InputConnection.commitText`.
2. **App:** onboarding (enable the IME, mic permission, model download), history, dictionary, settings, a record-to-clipboard screen and a Quick Settings tile.
3. Phase 5: the floating bubble + accessibility service for people who want to keep Gboard, with a disclosure screen and Wispr-style "Repair" recovery.

### 3.2 `hushflow-core` (Rust, UniFFI): what moves and what stays

Measured in this repo: 36K lines of Rust in `src-tauri/src`; the modules below import nothing from Tauri.

- **Moves into the core (≈8–10K lines, ~25% of the Rust):** `audio_toolkit/text.rs` (884 lines: rule-based cleanup, fillers, capitalization), `audio_toolkit/chunking.rs` and `vad/*` (Silero through transcribe-cpp, plus earshot), `managers/cleanup/{prompt,catalog}.rs`, the output guard and deadline logic from `cleanup/mod.rs`, `managers/transcription/{chunked,job,live,policy}.rs`, `gguf_meta.rs`, `catalog/`, `model/download.rs` (resumable, SHA-checked), and the SQLite stores (`history.rs` after removing its Tauri events, `meeting/store.rs`). A trait-based `SttEngine` / `CleanupEngine` API, so Swift and Kotlin can plug in SpeechAnalyzer, Foundation Models, Core ML Parakeet and LiteRT-LM.
- **Can't port as is:** `managers/cleanup/server.rs` spawns `llama-server`, and `engine_supervisor` spawns a worker process. **iOS doesn't allow child processes**, so on iOS anything we run ourselves links into the process. On Android the worker becomes an `android:process=":engine"` bound service that keeps the crash isolation.
- **Desktop-only:** `shortcut/`, `paste_tx/`, `clipboard.rs`, `overlay.rs`, `tray.rs`, `secure_input.rs`, `transcription_coordinator.rs`, the React UI.
- The desktop app should depend on `hushflow-core` too, so the cleanup prompt and guard stay identical on every platform. That refactor is worth doing even before mobile.

### 3.3 Runtime layout

```
iOS                                              Android
┌ Keyboard ext (Swift, <30 MB, no Rust) ┐        ┌ IME process (Kotlin) ───────────────┐
│ QWERTY + mic key, App Group I/O       │        │ AudioRecord 16 kHz → VAD (core)     │
└──────────────┬────────────────────────┘        │ commitText()                        │
     App Group files + Darwin notify             └──────────────┬──────────────────────┘
┌ Main app (background, audio session) ─┐               Binder (AIDL)
│ AVAudioEngine → VAD (core)            │        ┌ :engine process ────────────────────┐
│ SpeechAnalyzer │ Parakeet Core ML(ANE)│        │ transcribe-cpp Parakeet (core)      │
│ rules (core) → Foundation Models      │        │ LiteRT-LM Gemma 4 E2B │ Gemini Nano │
│ guard (core) → result file            │        │ rules + guard (core)                │
└───────────────────────────────────────┘        └─────────────────────────────────────┘
```

The keyboard extension links **no** Rust and loads no model. 30–60 MB doesn't leave room for that.

## 5. Note-taker on mobile

- **Reference:** Granola's iPhone app is built for in-person meetings on the phone's microphone, with start and stop from the lock screen and widgets. It keeps no audio ([App Store](https://apps.apple.com/us/app/6739429409), [tl;dv](https://tldv.io/blog/granola-review)).
- **iOS:** start in the foreground with a Live Activity. Recording continues on the lock screen through `UIBackgroundModes=audio`. When a call or Siri interrupts it, it can't restart from the background, so we post a notification ("Paused, tap to resume") and splice the segments. **During the meeting we only record**, writing a single-channel FLAC (NOTES_SPEC §4.1). In the background, live captions come from SpeechAnalyzer or Core ML Parakeet, and only if spike S2 passes. **After stop, in the foreground**, the full pass runs on Metal (`transcribe-cpp` Parakeet is fine in the foreground), and the enhanced notes come from Foundation Models with no rate limit, or rules-only plus the transcript on older phones.
- **Android:** a `microphone` foreground service started from the activity or a notification tap, with a persistent notification. OEM battery killers (Xiaomi, Samsung) need an "unrestricted battery" prompt. The finalize step and the notes use the `:engine` process and Gemma, the same as desktop.
- **Speakers:** mic-only, so the desktop's Me/Them split doesn't apply. The MVP is one speaker track. A later mobile phase reuses NOTES_SPEC's Phase 2 in-person mode (Sortformer 4-speaker, 139 MB GGUF) in the foreground pass. **No call recording:** the Play policy explicitly bars the accessibility API for call audio ([Engadget, 2022](https://www.engadget.com/google-is-banning-third-party-call-recording-apps-from-the-play-store-093201443.html)), and iOS offers no API for it.

## 6. Risks

| ------------------------------------------------------------------------------------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `transcribe-cpp` doesn't build for Android                                                             | Medium              | Spike S5.
